## 2. 测试总原则

本项目测试设计遵循以下总原则：

### 2.1 高危优先于完整
当时间有限时，优先守住：
- 盘面合成闭环
- 订单可达性与奖励正确性
- 活动、热更、弱网下的线上事故风险 fileciteturn0file4turn0file8turn0file3

### 2.2 数据正确优先于展示正确
当前项目里，比 UI 更重要的是：
- 合成结果对不对
- 奖励到账对不对
- 状态切换是不是唯一正确
- 主盘和活动盘有没有串数据
- 断网重连后有没有状态分叉 fileciteturn0file3turn0file9

### 2.3 闭环优先于单点
不能只分别测订单页、奖励页、剧情页。
必须按闭环测：

**订单目标可达 → 订单完成 → 奖励到账 → 奖励足以推进 → 剧情/装修触发 → 新阶段/新订单开放。** fileciteturn0file8

### 2.4 恢复性测试必须纳入主路径
盘面、奖励、剧情、活动等功能，都必须补看恢复态：
- 切后台
- 闪退
- 断网
- 重连
- 重登
- 多端切换 fileciteturn0file4turn0file8turn0file3

### 2.5 运营态测试不能只测“能不能开”
对于活动、热更、弱网，测试重点是：
- 生命周期正确
- 状态唯一正确
- 数据隔离正确
- 清理与恢复正确
- 奖励不多发不漏发 fileciteturn0file3

## 3. 当前项目的优先级定义

### 3.1 P0：严重事故级
满足任一情况，可判为 P0：
- 主盘面主循环被打断，无法完成“生成 → 合成 → 交付 → 推进”
- 核心物品链断链 / 错链 / 跳链，导致订单或主线不可达
- 订单为无解单，当前阶段没有合法来源
- 奖励重复发放、漏发、发错位置
- 订单完成后闭环断裂，无法继续推进剧情 / 装修 / 章节
- 活动盘与主盘串数据
- 热更导致盘面、订单、活动或旧存档损坏
- 弱网 / 重连导致重复提交、重复领奖、重复结算
- 客户端与服务端状态严重不一致，影响玩家资产或主线状态 fileciteturn0file4turn0file8turn0file3turn0file9

### 3.2 P1：高影响问题
满足任一情况，可判为 P1：
- 自动吸附、分支链、多来源链、容器规则错误，影响高频体验
- 多订单连续完成时弹窗 / 剧情 / 刷新链路冲突
- 活动阶段奖励、排行、锁榜、结算边界异常
- 跨日、刷新、限次、时效边界状态切换异常
- 恢复后状态最终可修正，但中途表现异常明显

### 3.3 P2：一般问题
满足任一情况，可判为 P2：
- 展示顺序、提示时机、普通分支流程异常
- 轻量边界下的体验不一致
- 低频交互或展示层小错误

### 3.4 P3：低影响问题
满足任一情况，可判为 P3：
- 一般文案问题
- 非阻断动画表现问题
- 轻微 UI 错位且不影响逻辑

## 4. AI 必测维度

任何新增功能，AI 都必须先判断是否需要覆盖以下维度：

- 主流程
- 分支流程
- 异常流程
- 边界条件
- 状态切换
- 重复点击 / 重复请求 / 并发
- 弱网 / 断网 / 重连 / 切后台 / 杀进程
- 跨天 / 活动开启关闭 / 热更配置生效边界
- 系统联动
- 回归影响

其中，当前项目对以下维度敏感度最高：
- 恢复态
- 满盘态
- 奖励落点
- 订单可达性
- 活动盘 / 主盘隔离
- 热更兼容
- 弱网幂等 fileciteturn0file4turn0file8turn0file3

## 5. 当前项目的高危关注点

### 5.1 盘面与物品链
重点关注：
- 物品丢失、重复、重叠、落位错误
- 满盘误判 / 满盘吞物
- 拖拽中切后台 / 闪退 / 弱网恢复后不一致
- 单链不可达、分支链错接、多来源链判断错误
- 链尾用途错误或中途断链 fileciteturn0file4

### 5.2 订单可达与闭环推进
重点关注：
- 当前阶段是否存在无解单
- 奖励是否正确、唯一到账
- 奖励是否足以支撑剧情 / 装修推进
- 剧情是否按条件触发、按顺序触发、跳过后状态正确
- 章节解锁和新订单刷新是否完整接上 fileciteturn0file8

### 5.3 活动生命周期与隔离
重点关注：
- 活动资格和入口状态
- 活动盘与主盘隔离
- 活动阶段奖励 / 排行 / 结算
- 活动结束清理与补发
- 活动边界时刻（开始前后、结束前后、锁榜、结算）状态是否正确 fileciteturn0file3

### 5.4 热更与配置切换
重点关注：
- 运行中热更是否安全中断和恢复
- 物品链、订单池、活动配置切换后的兼容性
- 旧存档对新配置的映射
- 热更失败或半更状态下的兜底逻辑 fileciteturn0file3

### 5.5 弱网 / 断网 / 重连
重点关注：
- 订单提交、奖励领取、结算确认、购买、活动领奖等操作是否具备幂等性
- 超时重试是否造成重复扣减 / 重复发放
- 重登后最终状态是否唯一正确 fileciteturn0file3turn0file9

## 6. 风险识别规则（真实项目版）

AI 在分析需求时，必须优先判断：

1. 是否改动盘面行为、物品链、生成器、满盘或恢复逻辑
2. 是否改动订单目标、订单池、奖励、主线推进或剧情触发条件
3. 是否涉及活动入口、活动盘、活动奖励、排行或活动结算
4. 是否涉及热更配置、旧存档映射、配置切换边界
5. 是否涉及奖励发放、邮件兜底、背包满 / 盘满落点处理
6. 是否涉及弱网、重试、断网、重登、多端恢复
7. 是否涉及跨日、限时、活动开始/结束、锁榜等时间边界
8. 是否改动了共享组件或公共链路（如弹窗队列、奖励组件、请求幂等）
9. 是否可能带坏旧功能
10. 是否存在玩家可利用路径

只要任意一项答案为“是”或“有可能”，都要增强该方向测试。fileciteturn0file3turn0file4turn0file8

## 7. 测试设计偏向（当前项目版）

当时间有限时，覆盖顺序建议固定为：

1. **主盘 / 主线主闭环**：生成、合成、交付、奖励、推进
2. **奖励与状态正确性**：到账、扣减、闭环是否接上
3. **恢复性与幂等性**：闪退、断网、重登、弱网、切后台
4. **时间边界**：跨天、活动结束、热更生效、锁榜、结算
5. **联动回归**：旧链路、共享链路、活动与主线交叉处
6. **展示细节**：红点、文案、提示节奏、动画细节

也就是说，AI 不能把主要精力花在“文案、普通 UI、小提示”，而应该优先守住事故路径。fileciteturn0file9turn0file3

## 8. 人工复核原则

AI 生成结果后，人工优先复核：
- 有没有漏掉“物品链可达性”
- 有没有漏掉“订单闭环断裂”
- 有没有忽略“活动盘与主盘隔离”
- 有没有忽略“热更兼容”
- 有没有忽略“弱网幂等”
- 回归范围是不是说得太大或太空

## 10. 当前结论

AI 后续生成测试分析和用例时，应始终优先守住：

- 盘面
- 物品链
- 订单闭环
- 奖励正确性
- 剧情 / 装修 / 章节推进
- 活动隔离与活动结算
- 热更兼容
- 弱网幂等
- 回归影响
