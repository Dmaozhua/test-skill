# 回归范围规则

## 1. 目标

约束 AI 在新增功能测试时，合理判断回归范围。

避免两种问题：

- 完全不提回归
- 无脑扩大成"全量回归所有系统"

---

## 2. 回归分层

### 必回归
满足任一条件：
- 直接修改的模块
- 共用核心逻辑
- 共用奖励/扣减/结算链路
- 涉及充值、奖励、资源、订单、邮件、背包
- 历史上出过类似严重问题

### 建议回归
满足任一条件：
- 存在状态联动
- 共用组件
- 共用配置模板
- 共用刷新/限次/进度逻辑
- 旧功能容易被新功能影响

### 抽查回归
适用于：
- 弱耦合模块
- 仅共享部分展示逻辑
- 理论相关但历史较稳定模块

---

## 3. 必须联想的对象

### 相同资源链路
- 相同资源的其他获取入口
- 相同资源的其他消耗入口
- 背包 / 邮件 / 商店 / 任务联动

### 相同奖励链路
- 其他领奖页面
- 邮件补发
- 背包到账逻辑
- 状态更新逻辑

### 相同支付链路
- 其他商店购买
- 限购商品
- 首充/首购状态
- 订单补单
- 发货状态更新

### 相同状态机
- 开启 / 进行中 / 完成 / 已领取
- 失败回滚
- 恢复逻辑

### 相同时间规则
- 跨天
- 周刷新
- 月刷新
- 活动开始/结束
- 时效道具到期

---

## 4. 输出要求

每个回归建议都必须写清：

- 模块名
- 回归原因
- 推荐重点验证内容

不能只写"建议回归 XXX 系统"。
