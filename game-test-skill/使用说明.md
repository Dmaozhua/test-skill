# game-test-skill 使用说明

## 1. 这套 test-skill 是干什么的

`game-test-skill` 不是一个单纯“让 AI 写测试用例”的 prompt 集合，而是一套面向当前游戏项目的测试知识工程。

它的目标是：

* 让 AI 理解当前项目的核心玩法与高风险链路
* 在新增需求进入时，结合项目历史和规则输出更贴合项目的测试分析
* 重点防守卡死、资源刷取、奖励异常、付费异常、状态错乱、活动边界、热更兼容、弱网幂等等高危问题
* 把每次测试产出和复盘继续沉淀，逐步让 AI 更像“懂项目的主测”

---

## 2. 当前适用项目范围

这套 skill 当前已经按 **Merge+Story** 类项目进行实战化整理，适用于以下闭环：

**盘面合成 → 订单交付 → 奖励回流 → 剧情/装修推进 → 活动运营循环**

当前项目知识重点已经围绕三块真实专项沉淀：

1. 盘面与物品链专项
2. 订单-奖励-剧情闭环专项
3. 活动 + 热更 + 弱网专项

因此，这套 skill 最适合用于类似 Gossip Harbor 这类 Merge+Story 项目的需求测试设计，而不是通用游戏项目直接套用。

## 3. 当前目录结构说明

```text
game-test-skill/
  ├─ README.md
  ├─ 01_project_context/
  │  ├─ 项目概览.md
  │  ├─ 测试策略.md
  │  ├─ 测试用例输出格式规范.md
  │  ├─ 边界测试清单.md
  │  └─ 回归范围规则.md
  ├─ 03_bug_memory/
  │  └─ 历史高危问题.md
  ├─ 04_feature_specs/
  ├─ 05_input_templates/
  │  └─ 项目资料采集模板.md
  ├─ 06_prompts/
  │  └─ system_prompt_v1.md
  ├─ 07_output_templates/
  │  └─ 测试用例输出模板.md
  └─ 08_runs/
```

各目录职责如下：

### `01_project_context/`

存放项目长期有效的测试知识，包括项目全局认识、测试策略、边界规则、回归规则、输出规范。
这一层决定 AI 是否真正理解当前项目。
### `03_bug_memory/`

存放历史高危问题。
这里不是普通 bug 清单，而是项目老坑记忆库，用于提醒 AI 主动防守重复发奖、资源刷取、状态错乱、活动结束边界异常等高价值问题。
### `4_feature_specs/`

用来存放**历史策划案、旧功能方案、旧版本改版说明、活动方案、旧配置说明**。

### `05_input_templates/`

存放资料采集模板。
用于首次接入项目，或在长期资料缺失时快速收集关键背景。

### `06_prompts/`

存放 AI 固定工作规则。
这里不负责存项目事实，只负责约束 AI 的思考顺序、风险扫描方式和输出顺序。

### `07_output_templates/`

存放标准输出模板。
用于统一 AI 产出的结构，方便复制到文档、表格、测试平台中。

### `08_runs/`

存放每次真实试跑记录。
每个新增需求都应在这里形成一份独立 run，用于沉淀输入、输出和人工复盘。

## 4. 运行流程

整套 skill 的运行流程可以精简为 6 步。

### 第 1 步：维护长期资料

先维护项目长期有效的知识：

* `项目概览.md`
* `测试策略.md`
* `边界测试清单.md`
* `回归范围规则.md`
* `历史高危问题.md`

这部分不针对某次具体需求，而是持续更新。
当项目主循环、活动策略、热更风险、弱网事故、历史高危问题发生变化时，需要及时修订。

### 第 2 步：准备本次新增策划案

每次收到一个新增需求时，在 `08_runs/` 下新建一个目录，例如：

```text
08_runs/
  2026-04-25_新活动阶段奖励改版/
    ├─ requirement.md
```

其中 `requirement.md` 就是本次新增策划案原文或整理版。

### 第 3 步：识别需求所属专项

在开始测试前，先判断本次需求主要属于哪类专项：

* 盘面与物品链
* 订单-奖励-剧情闭环
* 活动 + 热更 + 弱网

必要时可以同时属于主专项和次专项。
例如“活动阶段奖励调整”主属于活动专项，但次级会影响奖励发放、邮件补发、状态边界和回归范围。

### 第 4 步：组装本次输入包

每次喂给 AI 时，固定输入一般包括：

* `06_prompts/system_prompt_v1.md`
* `01_project_context/项目概览.md`
* `01_project_context/测试策略.md`
* `03_bug_memory/历史高危问题.md`
* `01_project_context/边界测试清单.md`
* `01_project_context/回归范围规则.md`
* `07_output_templates/测试用例输出模板.md`
* 本次 `requirement.md`

如果本次需求涉及某个旧功能的改版，还应额外补充对应的历史策划案或旧版本说明。

### 第 5 步：生成本次测试分析与用例

AI 必须按固定顺序输出：

1. 需求摘要
2. 影响范围
3. 风险分析
4. 测试点矩阵
5. 详细测试用例
6. 回归建议
7. 最危险问题提醒

输出内容不得跳过风险分析直接写步骤，也不得只写“正常流程”。
必须重点覆盖资源、奖励、付费、状态、边界、弱网、恢复、联动和回归。

### 第 6 步：沉淀结果与复盘

每次 run 结束后，建议目录结构如下：

```text
08_runs/
  2026-04-25_新活动阶段奖励改版/
    ├─ requirement.md
    ├─ input.md
    ├─ output.md
    └─ review.md
```

其中：

* `input.md`：记录这次喂给 AI 的资料组合
* `output.md`：记录 AI 输出结果
* `review.md`：记录人工复核意见、遗漏点和后续优化建议

如果本次测试中识别出新的高危模式，应回写到 `03_bug_memory/历史高危问题.md`，作为后续需求的长期风险记忆。

## 5. AI 生成测试时的固定原则

### 原则 1：先风险，后用例

先识别风险，再落成测试点和测试用例。
不允许直接写“功能正常即可”。

### 原则 2：高危优先

优先防守以下问题：

* 卡死 / 锁死 / 无法恢复
* 资源刷取 / 重复收益
* 奖励多发 / 漏发 / 错发
* 付费异常 / 订单异常 / 重复发货
* 活动边界异常
* 热更后状态断裂
* 弱网下幂等失效
* 客户端与服务端状态不一致

### 原则 3：专项优先于页面

测试不是只看页面是否能点，而是看专项闭环是否成立。
例如：

* 盘面专项看“生成-合成-交付-恢复”
* 订单专项看“可达-领奖-剧情推进-后续刷新”
* 活动专项看“开启-运行-边界结束-结算-清理-恢复”

### 原则 4：输出必须可执行

用例至少应具备：

* 用例标题
* 所属模块
* 优先级
* 风险标签
* 前置条件
* 操作步骤
* 预期结果

## 6. 推荐使用方式

### 场景 A：新增功能测试

适用于：

* 新生产器
* 新物品链
* 新订单池
* 新剧情节点
* 新活动盘
* 新排行榜奖励
* 新邮件补发逻辑

此时直接按标准流程跑一次 run。

### 场景 B：旧功能改版测试

适用于：

* 奖励规则调整
* 活动阶段奖励改版
* 订单奖励回流重做
* 体力恢复规则调整
* 热更配置替换

此时除本次需求外，建议额外补相关历史策划案和旧风险记录。

### 场景 C：高危事故预防性测试

适用于：

* 活动上线前
* 热更上线前
* 大版本切换前
* 跨日 / 结算 / 锁榜边界前

此时可以不等新增需求，也直接以“高危专题”方式跑专项测试分析。

---

## 7. 首次试跑建议

第一次使用时，建议不要选太大的需求，优先选择以下几类高价值需求之一：

* 新活动阶段奖励领取与活动结束边界
* 新生产器与物品链配置变更
* 新订单池与奖励回流调整
* 热更修改活动配置或物品链配置

这些需求既足够真实，又能快速验证 skill 是否真正识别高危风险。
当前真实项目里，活动边界、热更兼容、弱网幂等、物品链断裂、订单闭环断裂都是最值得先压的方向。

## 8. 常见错误用法

### 错误 1：只喂本次需求，不喂项目背景

结果会退化成普通 AI 写通用测试点，缺少项目感。

### 错误 2：把所有历史资料一次性全塞进去

结果会让上下文过重、重点模糊。
正确方式是：长期知识常驻，历史策划案按需补充。

### 错误 3：只看 output，不写 review

这样 skill 不会进化。
真正让 skill 越来越像项目主测的，是 review 后把新坑写回历史高危问题。

### 错误 4：只看主流程，不压边界

Merge+Story 项目最值钱的问题，往往藏在：

* 满盘
* 弱网
* 断线
* 活动结束前后
* 热更中断
* 奖励发放瞬间
* 章节切换瞬间

---

## 9. 最终目标

这套 skill 的最终目标不是“自动写文档”，而是形成一个可持续运转的测试设计闭环：

**长期知识维护 → 本次需求输入 → AI 生成测试分析 → 人工复核 → 新风险沉淀回知识库**

只要这个闭环跑起来，AI 产出的测试内容就会越来越贴近项目真实风险，而不是停留在通用模板层面。
