# 08_runs 标准运行模板

## 1. 这份模板是干什么的

这份文档用于统一 `08_runs/` 目录下每一次真实测试运行的组织方式。

目标只有一个：
**每来一个新增需求，都能快速、稳定地开一轮 test-skill 试跑，不靠临时想。**

它主要解决三个问题：

1. 本次新增需求放哪里
2. 本次喂给 AI 的输入怎么组
3. 本次输出结果怎么复盘、怎么沉淀

---

## 2. 每次 run 的标准目录结构

每来一个新增需求，都在 `08_runs/` 下新建一个目录。

推荐命名规则：

`日期_需求主题_轮次`

例如：

```text
08_runs/
  2026-04-25_新活动阶段奖励改版_首次试跑/
    ├─ requirement.md
    ├─ input.md
    ├─ output.md
    └─ review.md
```

如果是第二轮优化，可以写成：

```text
08_runs/
  2026-04-25_新活动阶段奖励改版_二次试跑/
```

或者：

```text
08_runs/
  2026-04-25_新活动阶段奖励改版_v2/
```

命名重点不是漂亮，而是让你以后能一眼找到：

* 什么时候跑的
* 跑的是什么需求
* 第几轮

---

## 3. 四个核心文件的职责

每次 run 固定保留这 4 个文件：

### 3.1 `requirement.md`

作用：

* 放本次新增策划案原文
* 或者放你整理后的需求摘要版

它回答的是：
**这次到底要测什么。**

---

### 3.2 `input.md`

作用：

* 记录这次实际喂给 AI 的资料组合
* 明确这次重点测什么、主专项是什么

它回答的是：
**这次 AI 是基于什么上下文开始分析的。**

---

### 3.3 `output.md`

作用：

* 放 AI 的正式产出
* 包括测试分析、测试点矩阵、详细用例、回归建议

它回答的是：
**AI 这次给出了什么测试结果。**

---

### 3.4 `review.md`

作用：

* 记录你人工复核的意见
* 记录 AI 漏掉了什么、哪里写得不准
* 记录哪些内容应该回写到长期知识库

它回答的是：
**这轮跑完之后，这套 skill 应该怎么变得更准。**

---

因为 AI 最怕的不是信息少，而是：
**信息很多但边界不清。**

## 5. `input.md` 模板

这是每次 run 最关键的文件之一。

它不是重复需求，而是明确：
**这次 AI 到底拿到了什么资料、应该按什么重点去想。**

```md
# input

## 1. 本次 run 基本信息
- run 名称：
- 日期：
- 轮次：首次试跑 / 二次试跑 / 回归补跑
- 需求类型：新增功能 / 功能改版 / 缺陷修复 / 配置调整 / 热更验证

## 2. 本次主专项归属
- 主专项：盘面与物品链 / 订单-奖励-剧情闭环 / 活动+热更+弱网
- 次专项：

## 3. 本次目标
- 本轮最想验证什么
- 本轮最担心什么事故

## 4. 本次输入资料清单
### 固定资料
- system_prompt_v1.md
- 项目概览.md
- 测试策略.md
- 历史高危问题.md
- 边界测试清单.md
- 回归范围规则.md
- 测试用例输出模板.md

### 本次需求资料
- requirement.md

### 本次额外补充资料
- 某历史策划案：
- 某旧版本说明：
- 某线上事故记录：

## 5. 本次重点风险
-
-
-

## 6. 本次希望 AI 重点回答的问题
- 这次需求会影响哪些旧系统？
- 最可能出哪些 P0/P1？
- 需要重点补哪些边界？
- 哪些回归是必带的？

## 7. 本次输出要求
- 是否更偏测试点矩阵
- 是否更偏详细用例
- 是否要压缩到 P0/P1 优先
```

### 使用建议

`input.md` 是你控制 AI 思路的地方。

以后你想让它：

* 更偏活动边界
* 更偏弱网幂等
* 更偏订单可达性
* 更偏盘面恢复一致性

都在这里写清，而不是临时口头补一句。

3. 这个漏判以后怎么变成长期记忆？

只要这三件事坚持做，这套 skill 就会越来越强。

## 8. 标准执行顺序

每次 run 都按这个顺序走：

### 第 1 步

新建 run 目录

### 第 2 步

把新增策划案整理进 `requirement.md`

### 第 3 步

写 `input.md`，明确：

* 主专项
* 本轮重点风险
* 本轮输入资料

### 第 4 步

把 `input.md + requirement.md + 固定资料` 一起喂给 AI

### 第 5 步

把 AI 输出存进 `output.md`

### 第 6 步

人工写 `review.md`

### 第 7 步

把 review 中有价值的新坑，回写到长期知识库

---

## 9. 什么时候该开新 run，什么时候不需要

### 建议开新 run 的情况

* 新功能
* 旧功能改版
* 活动新方案
* 热更配置变更
* 高危缺陷修复后验证
* 线上事故复盘后补专项

### 不一定要单独开 run 的情况

* 普通 UI 文案修改
* 低风险展示调整
* 已有 run 中的轻微补充

原则很简单：

**只要这次需求会影响测试重点、风险判断或回归范围，就值得单独开 run。**

---

## 10. 最终目标

`08_runs/` 不是临时缓存目录，而是：

**这套 test-skill 真正开始运转的地方。**

长期知识告诉 AI：

* 这个项目是什么
* 哪些地方危险

每次 run 告诉 AI：

* 这次改了什么
* 应该重点防什么

review 再把这次的经验反哺回去。

最终形成闭环：

**需求进入 → AI 分析 → 产出测试用例 → 人工复核 → 新风险沉淀**
